# 缓存命中率分析

> 数据来源：`~/.dsh/sessions/--<repo>-state-agents--/` 下 10 个 QQ 会话转录
> 统计时间：2026-10-12　│　样本：24,788 次 LLM 调用

## 结论

**模型侧前缀缓存命中率 = 97.41%**，覆盖 2026-08-31 ~ 2026-10-11 共 23 个有活动的日子，日均稳定在 95~99%。

## 怎么算出来的

DSH 把每次 LLM 调用的用量记在转录的 `assistant/message` 事件里，`data.usage` 形如：

```json
{"inputTokens": 1619, "outputTokens": 178, "cacheReadTokens": 18688}
```

**字段语义**（这是关键，容易读反）：

- `inputTokens` —— **未命中**缓存、需要重新计算的那部分
- `cacheReadTokens` —— **命中**缓存、直接复用的那部分
- 该 API 不返回 `cacheWriteTokens`，所以分母只有前两项

验证方法：把同一会话连续的 step 串起来看前缀增长链。第一步 `17792 → 18944 → 25088` 这种严格递增且每步等于「上一轮上下文 + 本轮新增」的关系，只可能是「已缓存的稳定前缀」，因此 `cacheReadTokens` 是命中量、`inputTokens` 是增量。另外 1589 次调用里只有 2 次 `cacheReadTokens = 0`，那 2 次正好是新会话的第一次调用——也和语义吻合。

```
命中率 = cacheReadTokens / (cacheReadTokens + inputTokens)
      = 12,223,775,365 / (12,223,775,365 + 325,401,894)
      = 97.41%
```

| 项目 | 数值 |
| --- | --- |
| LLM 调用次数 | 24,788 |
| 命中（缓存读） | 12,223,775,365 |
| 未命中（重新计算） | 325,401,894 |
| 输出 | 3,437,898 |

## 为什么这么高

上下文长是主因——**平均每次调用的上下文约 50.6 万 token**（中位数 52.4 万，P99 79.4 万，最大 90.5 万）。在这种长度下，每轮只有末尾新增的一小段（几百到几千 token）需要重新计算，其余全是可复用的稳定前缀，所以命中率天然逼近上限。

按轮内步序拆开看，能看出冷启动的代价：

| 位置 | 调用数 | 命中率 |
| --- | --- | --- |
| 每轮第一步 | 4,729 | 93.58% |
| 同轮后续步 | 20,060 | 98.39% |

同轮后续步几乎全命中；每轮第一步稍低，因为要带上新注入的用户消息。

## 按天趋势

命中率没有衰减迹象，但**未命中输入量在增长**（9 月 22 日约 700 万 → 10 月 10~11 日约 3,100~3,500 万），说明会话上下文在持续膨胀——每次调用要重新计算的绝对量变大了。这钱花在「长上下文里的新增部分」上。

## 本地缓存层（与上面无关，另一回事）

桥接自己维护的缓存，没有命中率埋点，只有静态规模：

| 缓存 | 实现 | 当前状态 |
| --- | --- | --- |
| 图库 | 按内容哈希落盘 `state/image-lib/` | 109 张 / 220.6MB（上限 300 张 256MB） |
| X 帖子配图 | `media-cache.mjs`，TTL 2 小时，上限 400 文件 / 200MB | 当前 0 文件（TTL 已清理） |
| X 译文 | `state/x-monitor-translations.json` | 35 条，无 TTL |
| 搜索引擎模块 | `web-search/index.mjs` 模块级缓存 | 引擎模块只加载一次 |
| 引擎断路器 | 失败后 5 分钟跳过该引擎 | 内存态 |

图库的 `useCount` 全为 0 且 `sent: 0`，说明这 109 张是拉取入库但还没被发出去用过——命中率无从谈起（分母为零）。

## 值得注意的两点

1. **冷启动几乎不影响总体命中率**。10 个会话的首次调用里，除 2 个全新会话（0%）外，其余都是 91~95%——因为 DSH 的 system prompt + 工具定义本身就有约 18k token 且已缓存。
2. **上下文长度是真问题**。平均 50 万 token 的上下文意味着即使 97% 命中，剩下 3% 的绝对量也随上下文线性增长（现在约 3,000 万/天）。若要压成本，压上下文长度比提命中率更有效。
